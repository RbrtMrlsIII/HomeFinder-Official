# 5.5G.6L — Browser Verification Architecture

## Status

**ARCHITECTURE DEFINED — IMPLEMENTATION DEFERRED**

This checkpoint establishes the durable browser-verification architecture for HomeFinder. It does not claim that Playwright or CI has already been installed or executed.

## Purpose

HomeFinder already has substantial MJS verification for contracts, routes, security, data, 3D, and integrations. Browser verification is an additional outer layer whose purpose is to prove that a real browser can execute critical user journeys through the actual UI.

The browser layer must not replace the existing verification system.

## Recommended Stack

**Playwright Test + Chromium + reproducible CI** is the approved initial architecture.

Playwright provides the browser test runner, assertions, isolation, reporting, tracing, and browser projects. Chromium is the first browser target because it is the smallest practical target for the current HomeFinder need. Additional browser/device projects remain future expansion points. Playwright supports Chromium, Firefox, WebKit, and device emulation without requiring a redesign of the test model. [Playwright installation and browser support](https://playwright.dev/docs/intro)

CI should provide a known browser-capable environment. Playwright documents installing browsers and operating-system dependencies with `npx playwright install --with-deps` and recommends a stable, reproducible CI configuration. [Playwright CI guidance](https://playwright.dev/docs/ci)

## Layered Verification Model

```text
Repository / Static Verification
        ↓
MJS Runtime / Contract Verification
        ↓
Browser E2E Verification
        ↓
Optional Real-Device Acceptance
```

### Layer 1 — Static

Proves repository structure, contracts, manifests, authority records, and other deterministic invariants.

### Layer 2 — MJS Runtime

Proves internal logic, route decisions, role rules, contracts, and other executable behavior without requiring a browser.

### Layer 3 — Browser E2E

Proves that actual UI interaction produces the expected navigation, authorization boundary, visible state, and browser behavior.

### Layer 4 — Real Device

Optional acceptance layer for mobile/desktop rendering, touch behavior, WebGL, viewport-specific behavior, and other device-specific concerns.

## HomeFinder Boundary

The browser test system is test infrastructure. It must not become a runtime dependency of the HomeFinder application.

The application should run normally without Playwright, Chromium, or CI.

## Initial Browser Project

Start with one logical project:

`chromium`

Do not add Firefox, WebKit, branded browsers, or mobile projects until evidence demonstrates a requirement.

Playwright projects are designed to permit later expansion across browsers, devices, environments, and test configurations. [Playwright projects](https://playwright.dev/docs/test-projects)

## Execution Environments

### Local development

Used for authoring, debugging, and targeted runs.

### CI

Used for reproducible acceptance and regression validation.

CI should install the exact project dependencies and Playwright browser dependencies from the repository's lockfile/configuration.

Playwright recommends a stable CI setup and notes that one worker can be preferable when stability and reproducibility are more important than throughput. [Playwright CI](https://playwright.dev/docs/ci)

## Evidence Architecture

Every browser run should produce concise machine-readable status and, when useful, richer diagnostic artifacts.

Minimum result:

- test name
- browser project
- environment
- result
- duration
- failure reason when applicable

Failure evidence may include:

- HTML report
- trace
- screenshot
- console errors
- network failures
- DOM evidence

Playwright's HTML report and Trace Viewer are intended for this purpose. [Running and debugging tests](https://playwright.dev/docs/running-tests) [Trace Viewer](https://playwright.dev/docs/trace-viewer-intro)

## Trace Policy

Do not record expensive traces for every successful test by default.

Preferred CI policy:

`trace: on-first-retry`

or an equivalent failure-focused policy.

Playwright explicitly recommends failure/retry-focused tracing rather than always-on tracing because of its performance cost. [Playwright tracing guidance](https://playwright.dev/docs/best-practices)

## Critical HomeFinder Journeys

The initial suite should remain small and high-value.

1. Guest journey
2. Seeker journey
3. Owner journey
4. Broker journey
5. Administrative/staff boundary journey where appropriate
6. House 1 → House 2
7. House 1 → House 3
8. House 2 → House 1 → House 3
9. House 3 → House 1 → House 2
10. Forbidden direct House 2 ↔ House 3 attempt
11. Role preservation across every permitted transition
12. Authorization preservation at the destination

The browser suite must reuse the existing route and authorization contracts rather than reimplementing them.

## Test Responsibility Rule

Do not use a browser test to prove a fact already adequately covered by a deterministic MJS test unless the browser is specifically verifying the UI integration of that fact.

Example:

MJS:

`House 2 → House 3 requires House 1`

Browser:

`A user clicking the House 3 control from House 2 cannot bypass the House 1 transition.`

## Environment Contract

The browser environment should define:

- Node version
- package manager
- lockfile
- Playwright version
- Chromium version supplied by Playwright
- operating-system assumptions
- base URL
- startup command
- test data strategy
- authentication strategy
- secret handling
- artifact retention policy

No environment-specific assumption should remain undocumented.

## Security

Browser reports, traces, screenshots, console logs, and network logs can contain credentials, tokens, test data, source fragments, or other sensitive information. They must be treated as controlled artifacts and uploaded only to trusted storage. [Playwright CI security guidance](https://playwright.dev/docs/ci)

Never place production credentials in browser tests.

Prefer dedicated test identities and non-production data.

## Acceptance Principle

Browser validation is complete only when:

`browser execution + critical journey coverage + expected UI state + authorization behavior + evidence`

are all established.

A successful Playwright installation alone is not browser validation.

## Non-Goals

5.5G.6L does not authorize:

- replacing MJS verification
- adding a large browser matrix
- introducing a second browser automation framework
- modifying production authentication merely to make tests easier
- storing secrets in test code
- weakening security to make browser journeys pass
- changing canonical SH3D authority

## Exit Gate

5.5G.6L can advance when:

- browser tooling is reproducibly installed
- Chromium launches in the intended environment
- the HomeFinder application can be served to the browser
- critical journeys execute
- role preservation is proven
- forbidden traversal is rejected
- browser evidence is retained
- failures can be diagnosed from artifacts
- the process is documented for another team member or AI session
