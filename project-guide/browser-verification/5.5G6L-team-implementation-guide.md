# HomeFinder Browser Verification — Team Implementation Guide

## Audience

For future AI sessions, limited-agent workflows, developers, and reviewers who need to implement or maintain browser verification without rediscovering the architecture.

## Before Starting

Read:

1. `project-guide/masterplan.md`
2. `project-guide/HandOver.md`
3. `project-guide/Endorsement.md`
4. `MASTER_SKILL.md`
5. the current checkpoint state
6. existing route/security/3D verification

Do not begin by creating browser tests blindly.

## Step 1 — Confirm the Application Entry Point

Determine:

- which page/app is the canonical browser entry point
- how it is served locally
- whether static hosting is sufficient
- whether a development server is required
- which assets must be available
- whether authentication requires a test backend

Record the answer before configuring Playwright.

## Step 2 — Inspect Existing Test Infrastructure

Before adding dependencies, inspect:

- `package.json`
- lockfile
- existing MJS scripts
- existing test directories
- existing local server scripts
- existing CI workflows
- environment/configuration files

Avoid duplicate runners.

## Step 3 — Add the Smallest Browser Layer

Use Playwright Test.

Initial browser project:

`chromium`

Do not activate a multi-browser matrix yet.

Playwright's standard installation can add the runner and browser binaries while preserving the existing project package structure. [Installation](https://playwright.dev/docs/intro)

## Step 4 — Define Browser Configuration

Configuration should establish:

- test directory
- Chromium project
- base URL
- application startup mechanism
- retries
- CI workers
- reporter
- trace policy
- timeout policy

The `webServer` configuration can launch a local application server before tests when required. [Configuration](https://playwright.dev/docs/test-configuration)

## Step 5 — Establish Test Identity Strategy

Do not use production accounts.

Determine whether browser tests need:

- guest state
- test seeker
- test owner
- test broker
- test admin
- test moderator
- test staff

Authentication setup must not bypass the actual authorization model.

If a test uses pre-authenticated state, the mechanism must be documented and separately verified.

## Step 6 — Build the Journey Matrix

Use the canonical role × house matrix.

For each journey define:

`role → starting house → action → allowed route → destination → expected UI state`

Also define forbidden transitions.

## Step 7 — Use Stable User-Facing Locators

Prefer accessible roles, labels, names, and stable semantic selectors.

Avoid selectors based on:

- generated CSS class names
- layout positions
- fragile DOM depth
- implementation-only IDs when a user-facing locator exists

The test should resemble a real user's interaction.

## Step 8 — Keep Tests Independent

A failed journey must not corrupt the next journey.

Each test should establish or reset the required state.

Do not depend on test execution order unless an explicit fixture/dependency is architecturally necessary and documented.

## Step 9 — Capture Failures Intelligently

Use the HTML report for overview and Trace Viewer for detailed failures.

A trace can preserve the action timeline, DOM snapshots, network activity, console information, and screenshots, making it useful for CI diagnosis. [Trace Viewer](https://playwright.dev/docs/trace-viewer-intro)

Do not generate heavyweight evidence for every successful run unless specifically needed.

## Step 10 — Run Locally First

Start with:

- one journey
- one browser
- one role
- one house transition

Then expand to the complete matrix.

Playwright supports headed mode, UI Mode, and targeted test execution for development/debugging. [Running tests](https://playwright.dev/docs/running-tests) [UI Mode](https://playwright.dev/docs/test-ui-mode)

## Step 11 — Move to CI

CI should:

1. check out the repository
2. install locked dependencies
3. install Playwright browser dependencies
4. start/build the required application environment
5. execute the browser suite
6. preserve reports/artifacts
7. fail the workflow on critical failures

Playwright documents this pattern for common CI systems. [CI](https://playwright.dev/docs/ci)

## Step 12 — Keep CI Reproducible

Initially prefer one CI worker for stability and reproducibility.

Do not optimize for parallelism until the suite is stable.

When the suite becomes large, sharding can be considered.

## Step 13 — Reconcile Browser Results

A browser failure should be classified as:

- application defect
- test defect
- environment defect
- test-data defect
- contract mismatch
- security/authentication issue
- timing/flakiness issue
- unresolved

Do not immediately weaken the test because it failed.

## Step 14 — Record Durable Evidence

Update the project with:

- browser architecture record
- implementation guide
- acceptance matrix
- execution result
- known limitations
- environment information
- next checkpoint

Do not leave critical knowledge only in CI logs or conversation history.

## Minimalism Rules

1. One browser framework.
2. One initial browser target.
3. One authoritative journey matrix.
4. Reuse existing contracts.
5. Reuse existing role definitions.
6. Reuse existing navigation logic.
7. Add browser tests only where they provide new evidence.
8. Prefer failure diagnostics over excessive always-on artifacts.
9. Do not create a parallel verification universe.

## When to Expand

Add another browser/device only when:

- a supported product requirement demands it
- a defect demonstrates browser-specific behavior
- deployment targets materially differ
- accessibility/device QA requires it

Record the reason before expanding the matrix.
