# HomeFinder Masterplan — Project Handover & Execution Authority

> **Purpose:** persistent orientation for future AI-assisted sessions. Read this file and `AI_ASSISTANT_READ_ME.md` before making architectural, repository, UI, backend, or 3D changes.

## 0. Target Goal

HomeFinder is being developed as a physically authored 3D presentation environment coupled to a conventional web application.

The target experience is:

```text
WEBSITE ARRIVAL
    ↓
TOP / ARRIVAL POV
    ↓
FRONT DOOR
    ↓ door opens
MAIN HALL
    ↓
hero / discovery / property / map / government / mission /
guide / safety / contact
    ↓
physical rooms, sections, tabs and UI objects
    ↓
additional houses
```

Camera movement must be physically valid:

- no wall penetration;
- no teleportation;
- no arbitrary camera coordinates generated by UI code;
- room-to-room traversal requires a valid opening/door;
- routes are spatial-authority concerns;
- UI/application code requests logical destinations only.

The application, backend, authorization, security and data contracts remain authoritative for application behavior. SH3D controls physical geometry and presentation.

### House 2 — Operations + Broker House

Operations/admin and broker experiences share the middle house.

Examples include:

- `admin.html`;
- `broker-hq.html`;
- operations/security/admin surfaces;
- broker dashboard/HQ/listing/client/transaction surfaces.

High-density UI must receive sufficient physical presentation space. Do not merge sections merely to reduce room count.

Seekers and owners share the third house.

Examples include:

- search/discovery;
- favorites/applications;
- seeker profile;
- owner properties;
- listings;
- owner analytics/profile;
- related sections and tabs.

House allocation is architectural; exact room allocation must be derived from the HTML/CSS/JS census.

## 4. Critical Current Problem

HTML sections, tabs and UI objects are not isolated markup.

They are targeted by:

- CSS selectors;
- responsive rules;
- JavaScript event handlers;
- animation code;
- state transitions;
- DOM queries;
- accessibility behavior;
- navigation logic.

Therefore a physical-room census cannot simply rename/move DOM elements.

Required dependency chain:

```text
HTML / DOM
   ↓
CSS consumers
   ↓
JS consumers
   ↓
animation/state behavior
   ↓
UI density
   ↓
logical presentation identity
   ↓
physical room
   ↓
camera
   ↓
door / route
```

A stable logical presentation ID should separate application/UI implementation details from SH3D camera identity.

Example:

```text
property.discovery
    ↓
PROPERTY_DISCOVERY_POV
    ↓
SH3D authored camera
```

CSS/JS selectors remain implementation details.

## 7. Repository / Test Strategy

The intended engineering gate is:

```text
npm run verify
    ├── test
    ├── naming
    ├── dependency boundaries
    ├── dead-code detection
    ├── HTML/reference integrity
    ├── 3D authority integrity
    ├── spatial-route validation
    └── documentation consistency
```

However, historical test failures must be classified first.

Classification:

```text
CURRENT CONTRACT
    → fix real defect

OLD CONTRACT
    → adapt/replace test or retire historical assertion

ARCHIVED / HISTORICAL
    → preserve as evidence

DELETE CANDIDATE
    → only when no runtime/test/contract/documentation/evidence purpose remains
```

Never restore WalkMyPlan just to make historical tests green.

No blind dead-code deletion.

### 7A. Minimal Knowledge Accretion

HomeFinder separates **evidence volume** from **project knowledge volume**. Findings may be numerous; durable AI memory must remain small.

The project uses this lifecycle:

```text
OBSERVE → RECORD → UNDERSTAND → CLASSIFY → ALIGN → VALIDATE
                           ↓
                 ENDORSE / REJECT / DEFER
                           ↓
              DISTILL DURABLE KNOWLEDGE
                           ↓
                AI_ASSISTANT_READ_ME.md
                           ↓
           ARCHIVE / DELETE REDUNDANT DETAIL
```

`project-guide/repository-governance/FINDINGS-TO-KNOWLEDGE.md` defines the operating procedure.

The design objective is **minimal repository footprint with increasing institutional knowledge**:

- detailed reports remain only where they have independent evidence value;
- reusable verified facts are distilled into the AI orientation layer;
- project-wide strategic decisions are also reflected in this masterplan;
- machine-readable authority remains in manifests/contracts rather than prose duplication;
- historical evidence is retained only when its evidentiary value justifies retention;
- redundant findings documents become deletion candidates only after their unique knowledge is promoted and their references/evidence roles are reconciled.

A finding becomes project knowledge only when it is **verified, reusable, actionable, stable enough for future sessions, and traceable to evidence**.

### Anti-trial-and-error principle

Each meaningful investigation should leave behind a compact memory of:

```text
HYPOTHESIS → TEST → RESULT → CORRECT INTERPRETATION → FUTURE ACTION / AVOIDANCE
```

Future agents must consult the distilled memory before reopening a disproven hypothesis. Repeating an old experiment requires new evidence or a changed contract, not simple forgetfulness.

This principle applies across frontend, backend, 3D, security, testing, repository hygiene, and documentation.

## 10A. Controlled Execution Branch — Architecture Validation Reconciliation

**Branch purpose:** establish a trustworthy validation baseline for the current HomeFinder architecture without changing the canonical SH3D or reviving superseded WalkMyPlan authority.

This branch is **inside** the master chronological plan. It does not replace the chronology and must rejoin it before three-house allocation / SH3D reconciliation proceeds.

### Branch point

Branch from the latest accepted project state after the existing Phase 5.5C census artifacts and current authority contracts.

```text
LATEST ACCEPTED STATE
        │
        └── Architecture Validation Reconciliation
                 │
                 ├── verify existing census
                 ├── classify current test failures
                 ├── reconcile WalkMyPlan tests
                 ├── reconcile stale repository-path tests
                 ├── identify genuine current-contract defects
                 └── establish reconciled validation baseline
                              │
                              ↓
                    rejoin master chronology
                              │
                              ↓
                    Three-house allocation
```

The repository already contains substantial census work. Therefore the objective is **not to recreate the census from zero**.

Existing evidence includes:

- `archive/csv-reconciliation/recovered-page-census.csv`

- `active_development/data/house-ui-ux-code-reality-map.json`

- `docs/md/3d-model-census-verified.md`
- current camera, route and spatial-authority contracts

The branch verifies and reconciles this evidence rather than discarding or duplicating it.

### First execution process

1. Run the repository test baseline without modifying architecture.
2. Record the exact test count and failures.
3. identify tests that reference retired WalkMyPlan authority.
4. identify stale repository-layout/path assumptions separately.
5. compare failing tests against the existing census and current contracts.
6. classify each test:
   - **CURRENT CONTRACT** → genuine defect candidate;
   - **SUPERSEDED WALKMYPLAN CONTRACT** → rewrite or archive;
   - **STALE REPOSITORY PATH** → repair only if the test remains current;
   - **HISTORICAL EVIDENCE** → preserve;
   - **UNCERTAIN** → investigate before modification.
7. Do not restore WalkMyPlan files to satisfy the baseline.
8. Do not modify `master/HomeFinder.sh3d` in this branch.
9. Produce a reconciled test manifest and explicit rejoin criteria.

### Reconciliation rule

A historical test is not a current defect merely because it fails.

```text
TEST FAILURE
    │
    ├── current contract ───────────→ investigate/fix
    │
    ├── WalkMyPlan authority ───────→ replace/archive
    │
    ├── stale repository path ──────→ repair if current
    │
    ├── historical evidence ────────→ preserve/archive
    │
    └── uncertain ──────────────────→ investigate
```

### Rejoin criteria

The branch may rejoin the master chronology only when:

- the existing census artifacts have been verified as the baseline;
- WalkMyPlan-dependent tests have explicit dispositions;
- current-contract tests are distinguishable from obsolete tests;
- no architectural decision requires restoring WalkMyPlan;
- a current validation baseline is recorded;
- canonical SH3D remains untouched;
- no accepted project progress has been dropped.

Only after these criteria are satisfied should the project proceed into **three-house room allocation and UI ↔ 3D presentation-contract reconciliation**.
