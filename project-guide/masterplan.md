# HomeFinder Masterplan — Project Handover & Execution Authority

> **Purpose:** persistent orientation for future AI-assisted sessions. Read this file and `AI_ASSISTANT_READ_ME.md` before making architectural, repository, UI, backend, or 3D changes.

## 0. Target Goal

HomeFinder is being developed as a physically authored 3D presentation environment coupled to a conventional web application.

The target experience is:

```text
WEBSITE ARRIVAL
    ↓
TOP / ARRIVAL POV
    ↓
FRONT DOOR
    ↓ door opens
MAIN HALL
    ↓
hero / discovery / property / map / government / mission /
guide / safety / contact
    ↓
physical rooms, sections, tabs and UI objects
    ↓
additional houses
```

Camera movement must be physically valid:

- no wall penetration;
- no teleportation;
- no arbitrary camera coordinates generated by UI code;
- room-to-room traversal requires a valid opening/door;
- routes are spatial-authority concerns;
- UI/application code requests logical destinations only.

The application, backend, authorization, security and data contracts remain authoritative for application behavior. SH3D controls physical geometry and presentation.

Examples include:

- `admin.html`;

Seekers and owners share the third house.

Examples include:

- favorites/applications;
- seeker profile;
- owner properties;
- listings;
- owner analytics/profile;
- related sections and tabs.

House allocation is architectural; exact room allocation must be derived from the HTML/CSS/JS census.

## 4. Critical Current Problem

HTML sections, tabs and UI objects are not isolated markup.

They are targeted by:

- CSS selectors;
- responsive rules;
- JavaScript event handlers;
- animation code;
- state transitions;
- DOM queries;
- accessibility behavior;
- navigation logic.

Therefore a physical-room census cannot simply rename/move DOM elements.

Required dependency chain:

```text
HTML / DOM
   ↓
CSS consumers
   ↓
JS consumers
   ↓
animation/state behavior
   ↓
UI density
   ↓
logical presentation identity
   ↓
physical room
   ↓
camera
   ↓
door / route
```

A stable logical presentation ID should separate application/UI implementation details from SH3D camera identity.

Example:

```text
property.discovery
    ↓
PROPERTY_DISCOVERY_POV
    ↓
SH3D authored camera
```

CSS/JS selectors remain implementation details.

### Execution principle

The UI-to-physical relationship is **not one UI object = one physical object**.

A single physical presentation object/zone may support multiple logical UI destinations or states when those destinations share:

- a presentation surface;
- a DOM root;
- a theme;
- an animation family;
- a camera framing;
- a stateful presentation object.

Conversely, one logical destination may require multiple physical presentation zones when UI density or interaction complexity requires it.

```text

presentation identities

camera states

route / door states
```

## 5.5G.6L — Browser Verification Architecture and Acceptance Gates

### Objective

Establish a durable browser-verification capability for HomeFinder so future developers or limited AI-agent sessions can validate actual user journeys rather than relying only on internal MJS logic.

### Architectural Decision

The approved initial browser stack is:

`Playwright Test → Chromium → reproducible CI`

Playwright is the browser automation/test layer. CI is the reproducible execution environment. These are complementary parts of one verification capability, not competing alternatives.

The browser layer supplements the existing MJS verification ecosystem and must not replace it.

### Verification Layers

```text
Static / structural verification
        ↓
MJS runtime / contract verification
        ↓
Browser E2E verification
        ↓
Optional real-device acceptance
```

The browser layer exists to prove UI-integrated behavior: actual clicks, visible state, browser navigation, authorization boundaries, and critical user journeys.

### Initial Scope

Begin with Chromium only.

Do not introduce Firefox, WebKit, branded browsers, or device projects until a product requirement or demonstrated defect justifies the additional matrix.

Playwright projects permit later expansion without redesigning the test architecture.

### Initial Critical Journeys

- Guest navigation boundary
- Seeker journey
- Owner journey
- Broker journey
- Administrative/staff boundary where applicable
- House 1 → House 2
- House 1 → House 3
- House 2 → House 1 → House 3
- House 3 → House 1 → House 2
- direct House 2 ↔ House 3 rejection
- role preservation across every permitted transition
- destination authorization preservation

### Evidence Strategy

Browser runs must produce compact status evidence. Failed or retried tests should provide diagnostic artifacts such as HTML reports, traces, screenshots, console information, and network information where useful.

Trace collection should remain failure/retry focused rather than always-on unless a specific investigation requires otherwise.

### CI Strategy

CI is the preferred reproducible browser environment.

The environment must document:

- Node/runtime version
- package manager and lockfile
- Playwright version
- Chromium version
- operating-system assumptions
- application startup command
- base URL
- test-data/authentication strategy
- artifact handling
- secret-handling rules

Initial CI execution should favor stability and reproducibility over parallelism.

### Security Boundary

Browser testing must never require production credentials.

Reports, traces, screenshots, console logs, and network logs are potentially sensitive and must be treated as controlled artifacts.
