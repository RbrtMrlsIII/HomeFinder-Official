## Important interpretation

Physical presentation is many-to-many.

- One physical room/object may support multiple logical UI states when CSS/JS roots, themes, animations, and responsive behavior cooperate.
- One logical destination may use multiple physical zones when its density or interaction model requires it.
- Page count and DOM-object count are not room counts.

## Why this is not yet topology

The spatial clusters are only evidence of candidate house allocation.

We have not yet established:

- which doors are authoritative entrances;
- whether the two clusters are internally walkable;
- whether a route can connect House 1 → House 2 → House 3;
- whether any corridor/threshold must be authored;
- whether existing web navigation already expresses an intended route;
- whether camera clearances are valid;
- whether elevations should be adjusted for a future physical world.

Therefore **no camera finalization and no route authoring is performed here**.

## Existing UI navigation preservation

The existing application navigation remains active evidence.

When route reconciliation begins, the procedure is:

1. observe current navigation behavior;
2. map logical destination transitions;
3. compare them with candidate physical doors/routes;
4. prove replacement behavior;
5. only then classify obsolete implementation as removable.

No old navigation code is deleted by this gate.

## Exit confirmation rule

A user confirms a logical journey once:

`current presentation → exit confirmation → physical route/doors → destination presentation`

Intermediate doors are traversal mechanics, not additional confirmation prompts.
