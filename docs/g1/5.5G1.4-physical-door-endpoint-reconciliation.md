# 5.5G.1.4 — Physical Door Endpoint Reconciliation

## Purpose
Resolve the six multi-endpoint door records against the actual F3-reconciled SH3D geometry, without implementing routes.

## Result

Six records were inspected using the door's own level and coordinates, then compared only with room polygons on that same level. This removes a major false-positive source from the earlier graph: stacked rooms from different levels cannot be treated as endpoints of the same door.

### Two records narrowed to a credible room pair

- `add-doorOrWindow-c7805654-0e93-4b58-9a34-5ee1ad3f5183` → Kitchen ↔ Hall candidate.
- `add-doorOrWindow-9df41ae2-c632-4510-a40d-f15c0a40fb83` → Hall ↔ adjacent unnamed room candidate.

These remain **route-unvalidated**.

### Four records remain ambiguous at the room-object identity layer

The four level-1 doors around Bedroom #2, Bedroom #3, Bathroom and the unnamed room are colocated with overlapping room representations. One room polygon is a semantic/visible room while another duplicate/non-floor polygon occupies essentially the same footprint.

Therefore the physical evidence currently proves a **room family/region**, but not a unique authoritative room object for the second endpoint.

This is not a reason to invent a binding.

## Critical finding

The earlier six-edge ambiguity was partly caused by graph construction failing to enforce the door's own level. G1.4 now treats level as a mandatory endpoint constraint.
