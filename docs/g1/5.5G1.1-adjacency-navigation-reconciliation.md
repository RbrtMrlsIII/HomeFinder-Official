# 5.5G.1.1 — Adjacency ↔ Existing Navigation Contract Reconciliation

## Purpose

Compare the physical adjacency evidence from G1 against the application's existing navigation evidence **without implementing routes**.

## Application evidence

The application currently expresses route intent through:
- HTML anchors between pages;
- JavaScript `location.assign`, `window.location`, and `window.goTo` compatibility/cinematic routing;
- authentication/role redirects;
- the active `ui-response-mapping.json` contract.

The active UI-response mapping explicitly states that the Sweet Home 3D model is architectural authority while the application remains application authority.

It also names logical door contracts such as:
- `main-door`
- `market-door`
- `gov-door`
- `profile-door`
- `broker-hq-door`
- `login-door`
- `exit/contact doors`

## Reconciliation result

The physical census has adjacency candidates, but the current application does **not** bind individual SH3D door object IDs to those logical door names.

Therefore:

`logical destination → application route` is established,

but:

`logical door → physical door object → validated route`

is **not yet established**.

This is the correct boundary to preserve.

### Important consequences

1. The public Front door is an exterior-boundary candidate, but its object ID is not yet contract-bound to `main-door`.
2. Additional-model doors remain physical evidence only. Their existence does not authorize a runtime House 2/House 3 transfer.
3. Existing HTML/JS navigation should not be replaced during this gate.
4. The camera rig remains a presentation mapping, not a route authority.
5. No route is physically validated by this reconciliation.

## Findings

The current code already contains enough logical navigation evidence to tell us **where the application wants to go**, but not enough physical binding evidence to tell us **which authored door and route should carry the user there**.

That is exactly the seam the next spatial gate should resolve.

## Changes

- Added machine-readable route evidence.
- Added logical-door contract inventory.
- Added physical-adjacency ↔ application-navigation reconciliation.
- Updated continuity state and institutional documentation.
- **No runtime code changed.**
- **No SH3D changed.**
- **No candidate promoted.**

## Next gate

Build a stable candidate adjacency graph with explicit exterior and house-boundary nodes. Then test only the transitions actually required by current application contracts.

Route implementation remains prohibited until those graph paths are physically validated.
